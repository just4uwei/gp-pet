# 迭代流程

这个 skill 解决一件事：**每次新会话不用花两小时重建上下文**。

系统分三层，只有中间一层需要每次读：

| 层 | 内容 | 什么时候读 |
|---|---|---|
| 约束层 | `CLAUDE.md` · 4 份 ADR · `docs/01`–`10` | 已在系统提示里；只在动到对应模块时深读 |
| **状态层** | **`pnpm iterate` 的输出** | **每次会话开头，必读** |
| 流程层 | `docs/07 §3.6`（改动门槛）· M2 清单 4.9（归档流程） | 真要动手时才读 |

---

## 第一步：永远先跑这个

```bash
pnpm iterate
```

它从**真实数据源**算出当前状态，不依赖任何手写的进度记录（那种东西会过期——
CLAUDE.md 里「`risk`/`multiTf` 一个网格都没跑过」那句挂了一整个阶段就是先例）：

- 引擎版本与 62 个叶子参数的六档归档 ← `paramRows()`，有测试钉着
- 最新回测基线 ← `reports/calib/*.json`
- **alpha 配对胜率** ← `reports/calib/random-*.json`
- 真机运行数据 ← `%APPDATA%/gp-pet/market.db`（只读打开）
- 测试集预算 ← `docs/07 §3` 那行计数

**读不到的东西它会说「读不到」，不会显示成 0。** 看到 ⚠ 就当真——
把「没测过」读成「0 次」正好反了。

想把快照写进版本控制（`reports/` 是 gitignored 的，换台机器就没了）：

```bash
pnpm iterate -- --write   # 刷新 docs/iteration/看板.md
```

## 第二步：按看板的四个桶决定做什么

看板把任务分成四桶，**它们的处理方式完全不同**：

### 「只能靠时间」——不要试图用工程绕过

M1 跑满一天、M3 自用一周、影子净值点、闸门漏斗数据。
这些没有工程替代品。看到它们**只需要确认用户知道**，不要提方案。

### 「现在就能做」——这才是可以动手的

通常是工程缺口或不一致（基线版本与引擎版本对不上、量表零数据之类）。

### 「等你拍板」——报门槛，不提候选

⚠ **这是授权边界（2026-08-15 拍板），最容易越界的地方。**

看板只说「下一轮改动的前置条件达成了没」。**候选由用户提，或在会话里讨论产生。**
不要主动生成「今天建议改 X」——每天的信息增量只有 **0.048%**
（261 只新增 1 根 ÷ 54.5 万根），一个每天产出改进建议的循环必然是在同一份数据上
反复搜索，那是过拟合的定义。

### 「明确不做」——看到就打断

比如「继续为清 `BLOCKED` 跑 OFAT 网格」。八张网格 82 组候选已经跑完，
出厂值被红线淘汰 ⇒ 裁决必为 `INCONCLUSIVE` ⇒ 产出**零证据**，不是弱证据。

## 第三步：真要改判定逻辑时，走这个顺序

**顺序不能换。** 判据必须在看到结果之前定下来，否则就是自己给自己找台阶。

1. **先写论证** → `docs/04`（或 `docs/05`）加一节，**必须包含「这条论证可能错在哪」**。
   一条只能事后解释、无法事先陈述的规则，与对着数据刻出来的规则在形式上无法区分。
2. **确认判据** → 读 `docs/07 §3.6` 的四条门槛。不要凭记忆，那一节会更新。
3. **才动代码** → 改完递增 `ENGINE_VERSION`。
4. **补测试** → ⚠ 见下面「测试的一个坑」。
5. **跑验收** → 基线重跑 + `pnpm audit:random --match-regime --shuffle-spans`。
   **每个候选机制只报一次分位**，不许反复调到达标为止——那等于把随机基准变成
   新的过拟合目标，而它是目前唯一可信的判据。
6. **归档** → M2 偏差报告新增一节 + CHANGELOG + 更新 `params-view.ts` 的 `STATUS`
   + **更新 CLAUDE.md 概述**（第 6 步最容易漏，docs/09 §1.1 那个过期说法就是这么来的）。

### 测试的一个坑

**没有任何 fixture 能走到 `TREND_UP`**（实测三个突破类 fixture 在关键根上全是 `TRANSITION`，
`rangeBound` 是 `RANGE`）。所以「造一个上升趋势 fixture 然后断言某信号不触发」
会**因为构造不出那个状态而假通过**——与 §5.19 那六条从未绿过的用例是同一形状。

正确写法：**同一根 K 线、同一套指标，只换 `ctx.regime`** 的对照。
先用能触发的那一档证明原始条件确实都成立，再换成目标状态看它消失。
现成例子在 `tests/unit/strategies/trend.test.ts` 的「TREND_UP 里 BUY 不计票」那一组。

## 读数纪律（每次看数都要过一遍）

这几条是踩出来的，不是推出来的：

1. **判据是 alpha 配对胜率，不是绩效。** 绝对收益、Calmar、夏普都会把 beta
   与「少做」记成策略的功劳。今天砍掉 9.6% 交易让全期从 −0.94% 变 −0.09%——
   那**不是**策略变好了。
2. **加权与中位背离时以中位为准。** 一笔妖股能翻转加权的符号：
   `T1+T2+T3+T4` 的加权 95 分位对应中位 0 分位，元凶是 SZ002969 一笔 **+325.8%**。
3. **凡是拿真实 `holdingBars` 做配对的读数都被内生性系统性压低**，
   要看 `--shuffle-spans` 那一档（`TREND_UP` 3.5% → 19.5%，差一倍）。
4. **胜率有两个口径**：逐笔 28.45% vs 建仓级 44.85%，同一份数据。用户体验到的是后者。
5. **砍掉一批负 alpha 交易必然提升剩余的 alpha——那是算术不是发现。**
   所以「砍掉一批」类改动必须额外过子集稳定性检验（四个切法都同向），
   否则分不清「找对机制」与「删掉任何一批差交易」。

## 做完之后

更新对应的出处，**一件事只有一个出处**：

| 内容 | 出处 |
|---|---|
| 实验过程与数字 | `docs/notes/M2-偏差报告.md` 新增一节 |
| 决策与候选清单 | `docs/notes/下一阶段取舍与迭代计划.md` |
| 参数归档状态 | `src/main/settings/params-view.ts` 的 `STATUS`（有测试拦漏归档）|
| 引擎行为变更 | `CHANGELOG.md`（写清动了什么、依据、**什么条件下结论失效**）|
| 状态快照 | `pnpm iterate -- --write` |

**看板本身不记决策**——它是全自动生成的，手改会被下次刷新覆盖。
