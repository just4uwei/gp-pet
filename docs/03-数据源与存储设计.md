# 03 · 数据源与存储设计

## 1. 数据需求盘点

| 数据 | 频率 | 用途 | 必需 |
|---|---|---|---|
| 日线 K（开高低收、成交量、成交额、复权因子） | 每交易日 1 次，回补 ≥ 300 根 | 全部指标计算的基础 | ✅ |
| 实时快照（最新价、今开、最高、最低、昨收、成交量、涨跌停价） | 盘中 10–120s | 构造「临时当日 K 线」，产出盘中预警 | ✅ |
| 周线 K | 由日线本地聚合，不单独拉取 | 多周期共振验证 | ✅ |
| 证券基础信息（名称、所属行业、上市日） | 首次 + 每周 | 展示、行业集中度 | ✅ |
| 交易日历 | 每周刷新 | 判断是否开市、指标的「交易日」口径 | ✅ |
| 60 分钟 / 30 分钟 K | 盘中 | 更精细的多周期验证 | ⬜ P2 |

## 2. 数据源策略

### 2.1 适配层

```ts
// src/main/providers/types.ts（骨架阶段仅契约）
export interface QuoteProvider {
  readonly id: 'eastmoney' | 'sina' | 'tencent'
  readonly capabilities: { daily: boolean; snapshot: boolean; minute: boolean; profile: boolean }
  fetchDaily(code: SecCode, from: TradeDate, to: TradeDate, adjust: AdjustMode): Promise<Candle[]>
  fetchSnapshots(codes: SecCode[]): Promise<Snapshot[]>   // 必须支持批量
  fetchProfile(code: SecCode): Promise<SecProfile>
}
```

三个实现：

| Provider | 承担 | 说明 |
|---|---|---|
| `eastmoney` | 主源：日线（含前复权）、快照、基础信息 | 字段最全，支持批量快照与分钟线 |
| `sina` | 备源：快照 | 极轻量，批量代码拼接在 URL 里，延迟低 |
| `tencent` | 备源：快照、日线 | 与新浪字段格式不同，作为第三兜底 |

**具体 URL 与字段映射不写进设计文档**，而是每个 provider 目录下配一份 `README.md` + `tests/fixtures/` 里的真实响应样本快照。理由：非官方接口会变，文档会过期，而 fixture 会让测试直接失败并指出变更位置。

### 2.2 降级与健康度

```
ProviderRegistry.pickFor(capability)
  按 settings.providerPriority 顺序尝试
  单次请求：超时 3s，重试 1 次（指数退避 300ms）
  连续失败 3 次 → 标记 provider 为 DEGRADED，冷却 5 分钟，跳到下一个
  全部 DEGRADED → 返回缓存数据并置 stale=true，UI 显示「行情离线」
  每次成功/失败都写 provider_health（滑动窗口成功率、p95 延迟）
```

**一致性校验**：当两个源同时可用时，抽样比对最新价，偏差 > 1% 记一条 `provider_health` 告警。免费源偶发返回陈旧或错位数据，这类静默错误比请求失败更危险。

### 2.3 复权口径

- 指标计算**统一使用前复权（qfq）日线**。除权日的价格跳空会伪造出金叉/死叉，这是最容易被忽略的信号污染源。
- 展示层（面板价格、涨跌幅）使用**不复权**真实价，与用户在券商 App 看到的一致。
- 持仓成本止损计算使用**不复权**价，因为用户的成本是真实成交价。
- 两套价格分别落库，`kline_daily` 同时存 `close` 与 `close_adj`。

### 2.4 请求礼节（自我限制）

免费接口没有配额说明，但滥用会被封。硬性上限：

- 全局并发 ≤ 4，单 provider 并发 ≤ 2
- 快照必须批量：一次请求携带全部自选股代码（分片 ≤ 50 只/请求）
- 日线只做增量：本地最后一根日期 +1 起拉；无缺口则整轮跳过
- 休市期间**完全不发请求**（除每周一次的日历与基础信息刷新）
- 统一 UA、开启 keep-alive，不伪造 Referer 之外的任何身份信息

按 100 只自选股、30s 轮询、4 小时交易时段估算：480 tick × 2 请求 ≈ **每日 < 1000 次请求**。

### 2.5 用户触发的取数：当日分时（2026-08-14）

上面那份预算算的是**轮询**。分时是全应用**唯一**一处由用户交互直接触发的取数，
不在其中，规矩也不同：

| | 轮询（快照 / 日线） | 分时（`fetchMinutes`） |
|---|---|---|
| 触发 | 调度器，每 30s | 用户打开抽屉「行情」页 |
| 范围 | 整个自选列表（批量） | 一只票 |
| 闸门 | 全局 ≤ 4 / 单源 ≤ 2 + 休市不发 | 同左，外加 **30s 结果缓存 + 在途请求合并** |
| 量级 | 每日 < 1000 次 | 用户点开几次就是几次 |

**这不是把 §2.4 放宽了，是它管不到的一类。** 分时能加进来的前提恰恰是它的量由人决定：
用户一天点开二十次抽屉也就二十次请求，与轮询不在一个量级。因此三条边界必须守住：

1. **不许从 tick 里调 `fetchMinutes`。** 那会把「一次一只票」变成
   「每 30 秒一整个自选列表」—— 上面那份预算的几十倍，而且没人会立刻发现。
2. **缓存是它自己的闸门**（`src/main/engine/intraday.ts` 的 `createMinuteCache`）：
   缓存的是 Promise 不是结果（连点两次共用一趟），失败的立即剔除
   （缓存住一个错误 = 把网络抖动钉死 30 秒，用户点「再看一次」还是那个错）。
3. **它不许污染 provider 健康度的口径**：registry 的 `fetchMinutes` 刻意不传
   `emptyIsFailure` —— 停牌股与开盘前请求会合法地返回 0 个点，把它记成失败会一路
   降级三个源、跳熔断，进而拖累 tick 路径，还会污染 docs/08 M1 的「成功率 > 99%」出口指标。

拉不到时退回本机留痕 `quote_tick`（§4.3），`IntradaySeries.source` 如实标 `LOCAL`，
**两份数据不合并** —— 分钟收盘价与 30s 快照是两种采样口径，拼在一条线上会出现
肉眼可见的锯齿，而用户没有任何办法看出那是两个来源。

**休市日这类接口返回的是上一个交易日的曲线**，因此 `MinuteSeries.tradeDate` 取自
数据本身而不是本机日期，落在请求窗口外时整段作废。默认当成今天画会得到一张
日期错位、图上却毫无破绽的假曲线。

## 3. 交易日历与时段状态机

日历来源：主源接口的日历数据；拉取失败时退化为「周一至周五 + 内置节假日表（`resources/holidays.json`，需每年更新）」，并在 UI 提示日历可能过期。

时段状态机（Asia/Shanghai）：

| 状态 | 时间 | tick 间隔 | 引擎行为 |
|---|---|---|---|
| `CLOSED` | 非交易日 / 15:00 之后 | 5 min 心跳 | 不拉行情 |
| `PRE_OPEN` | 09:00–09:15 | 1 min | 补齐日线缺口，预热指标 |
| `AUCTION` | 09:15–09:25 | 30 s | 只更新价格展示，**不产出信号**（集合竞价虚价） |
| `PRE_TRADE` | 09:25–09:30 | 30 s | 同上 |
| `CONTINUOUS_AM` | 09:30–11:30 | 可配 30 s | 正常产出盘中预警 |
| `LUNCH_BREAK` | 11:30–13:00 | 5 min | 不拉行情 |
| `CONTINUOUS_PM` | 13:00–14:57 | 可配 30 s | 正常产出；14:50 后买入信号降级为「次日观察」（T+1） |
| `CLOSING_AUCTION` | 14:57–15:00 | 10 s | 只更新价格，不新增信号 |
| `SETTLE` | 15:00–15:10 单次 | — | **确认轮**：用收盘线重算，升级/作废当日 provisional 信号 |

北交所 / ETF 时段与沪深一致，故不单列。若后续接入其他品种，状态机以 `MarketProfile` 配置驱动而非硬编码。

### 3.1 时钟校准（2026-08-15）

上面这张表的每一行都在问「现在几点」，而答案原先完全来自本机系统时钟。
时区那一层早就不依赖本地了（`scheduler/clock.ts` 用写死的 +08:00），
**依赖本地的是 epoch 本身**。

**为什么值得做**：应用对时间的敏感度是分钟级 —— 时段边界、`T1_LATE_BUY` 的尾盘窗口
890–910、做T的 14:50 边界、量比的时间归一化。最脏的一条在风控里：
`src/core/risk/index.ts` 的 `age = input.now.atMs - snapshot.at`，**左边本地钟、右边远端成交时刻**。
本机快 6 分钟 ⇒ 连续竞价里每条快照都判 `STALE_SNAPSHOT: SUPPRESS` ⇒ 买入信号整批被压掉，
而日志只说「行情已 6 分钟未更新」。

**时间源是 HTTP `Date` 响应头**，搭盘中每 30s 一次的快照请求取样，零额外请求
（`net/http.ts` 的 `onTiming` → `scheduler/clock-sync.ts`）。
休市不发请求 ⇒ 没有样本，所以启动与休眠唤醒后各主动探一次（只拉基准指数一只，
走已有 registry 路径，自带 5 分钟节流）—— 这几次请求计入 §2.4 的预算，量级可忽略。

**⚠ 不用 `Snapshot.at` 校时。** 三家 provider 都解析了它，看着像现成的源，
但那是「最后成交时刻」不是「服务器当前时刻」：停牌、冷门股几分钟没成交、收盘之后
它都会合法地落后，于是「远端比本地小」既可能是本地快了、也可能只是没人成交，
**两者无法区分**。它只是下界。

**两条纪律**：

1. **首次直接采用，之后每轮最多挪 ±2s。** 冷却窗口、每小时配额、跨日重置全部假设
   `now` 单调递增 —— 一次几分钟的回拨会让刚发过的提醒重新变成「冷却已过」。
   首次安全是因为那一刻 `AlertDispatcher` 的状态全是空的。
2. **只有答「现在几点」的地方用校准钟**（调度器、取数编排、落库时刻），
   **量「过了多久」的一律用本地钟**（`latencyMs`、provider 健康统计、分时 30s 缓存 TTL）。
   混用的后果是校准量一挪，正在计时的请求算出个偏了的延迟，污染健康统计。
   两个钟在 `data-layer.ts` 里显式分开，不要合并回去。

偏差 ≥ 60s 时面板出一条 info 横幅，文案必须说清**已经校正**——
否则会被读成「软件在带病运行」。

面板底部常驻一个时钟，画的就是这个校准后的北京时刻（`FooterClock`）——
**不是系统托盘那个**。两者在「机器不在 +08 时区」与「本机时钟真偏了」时会不一样，
而那正是需要一眼看见的时候。拿不到校时样本时它显式标「（未校准）」，
不静默退化成本机钟。

## 4. 本地存储

### 4.1 位置与形态

```
%APPDATA%/gp-pet/
├─ settings.json          应用设置（人类可读、可手改、启动时 schema 校验）
├─ market.db              SQLite：K 线、指标缓存、信号、提醒日志、自选股、持仓、影子账本
├─ market.db.bak-<n>      迁移前的一次性备份，只留最近 1 份（见 §4.4）
├─ backups/               周期备份 market-YYYY-MM-DD-HHmm.db，留最近 3 份（M4，见 §4.5）
└─ logs/main-YYYY-MM-DD.log  按天分文件，保留 7 天（含今天）；单日超 5MB 归档为 .old.log
```

> `settings.json` **始终留在默认位置**。设置里的「数据目录」（`AppSettings.dataDir`）
> 只搬 `market.db` 与 `backups/` —— 把配置也搬走的话，一旦它被改坏就再也找不回来了。

配置用 JSON 而非入库：用户可直接编辑、可备份、出问题时能手工修复。业务数据入 SQLite。

**个人配置的导入导出**（面板头部两个按钮，`src/main/settings/transfer.ts`）：

导出文件是一份带 `format` / `version` 头的 JSON，内容只有三样 ——
`settings.json` 全量、自选股（含分组与排序）、手工录入的持仓。
K 线、指标、信号、提醒日志一概不带：它们是**可再生的派生物**，
而且搬到另一台机器上会与本机行情对不上（提醒日志里写的是「那台机器当时发没发」）。

导入是**覆盖式**的：自选与持仓整份替换，动手前弹一个系统模态框报出将被清除的条数，
整个写入过程包在一个事务里。解析沿用 `sanitizeSettings()` 的取向 ——
坏字段退回默认值、坏行丢掉并各留一条 warning 回到界面上，**不整份拒绝**，也不静默。
两条约束在解析期就守住：`position.code` 是指向 `watchlist` 的外键（不在自选里的持仓行直接丢弃），
`isST` 不进文件（它从名称推出来，导出之后可能已经摘帽）。

### 4.2 Schema（`src/main/storage/migrations/`）

```sql
-- 自选股
CREATE TABLE watchlist (
  code            TEXT PRIMARY KEY,          -- 规范化代码，如 'SH600000'
  name            TEXT NOT NULL,
  market          TEXT NOT NULL,             -- SH | SZ | BJ
  board           TEXT,                      -- MAIN | GEM | STAR | BSE | ETF
  industry        TEXT,
  group_name      TEXT NOT NULL DEFAULT '自选',
  sort_order      INTEGER NOT NULL DEFAULT 0,
  strategy_override TEXT,                    -- JSON，null 表示用全局参数
  created_at      INTEGER NOT NULL
);

-- 日线（前复权与原始价并存）
CREATE TABLE kline_daily (
  code       TEXT NOT NULL,
  trade_date TEXT NOT NULL,                  -- 'YYYY-MM-DD'
  open REAL, high REAL, low REAL, close REAL,
  open_adj REAL, high_adj REAL, low_adj REAL, close_adj REAL,
  volume INTEGER, amount REAL,
  turnover_rate REAL,
  adj_factor REAL,
  provider   TEXT NOT NULL,
  PRIMARY KEY (code, trade_date)
);
CREATE INDEX idx_kline_code_date ON kline_daily(code, trade_date DESC);

-- 指标快照（只存每日收盘值，用于面板图表与回溯，盘中值不落库）
CREATE TABLE indicator_daily (
  code TEXT NOT NULL, trade_date TEXT NOT NULL,
  payload TEXT NOT NULL,                     -- JSON: IndicatorSet
  engine_version TEXT NOT NULL,              -- 参数或算法变更即失效重算
  PRIMARY KEY (code, trade_date)
);

-- 信号
CREATE TABLE signal (
  id           TEXT PRIMARY KEY,             -- uuid
  code         TEXT NOT NULL,
  created_at   INTEGER NOT NULL,
  trade_date   TEXT NOT NULL,
  direction    TEXT NOT NULL,                -- BUY | SELL | REDUCE | HOLD_WARN
  score        REAL NOT NULL,                -- 0..1 加权得分
  votes        INTEGER NOT NULL,             -- 一致子信号数
  regime       TEXT NOT NULL,
  stage        TEXT NOT NULL,                -- PROVISIONAL | CONFIRMED | INVALIDATED
  price_at     REAL NOT NULL,
  evidence     TEXT NOT NULL,                -- JSON: 逐条子条件 + 当时指标值
  engine_version TEXT NOT NULL
);
CREATE INDEX idx_signal_code_time ON signal(code, created_at DESC);

-- 实际提醒记录（用于去重、冷却与「我到底被提醒过什么」审计）
CREATE TABLE alert_log (
  id         TEXT PRIMARY KEY,
  signal_id  TEXT NOT NULL REFERENCES signal(id),
  level      TEXT NOT NULL,                  -- L1 | L2 | L3
  -- 逗号分隔的渠道列表，被丢弃的候选存 'NONE'。现役取值只有 PET（状态点）与 BUBBLE；
  -- TRAY / OS_NOTIFY 是 2026-08-13 之前的历史值，仍会出现在旧行里，读取端不过滤
  channel    TEXT NOT NULL,                  -- PET | BUBBLE | NONE（历史：TRAY | OS_NOTIFY）
  suppressed_reason TEXT,                    -- 非空表示被抑制及原因
  read_at    INTEGER,
  created_at INTEGER NOT NULL
);

-- 用户手工记录的持仓（仅供风控提醒计算）
CREATE TABLE position (
  code       TEXT PRIMARY KEY REFERENCES watchlist(code),
  shares     INTEGER NOT NULL,
  cost       REAL NOT NULL,                  -- 不复权成本价
  peak_price REAL,                           -- 持有期最高价，用于回撤/移动止损
  opened_at  INTEGER NOT NULL,
  note       TEXT
);

CREATE TABLE trade_calendar (
  trade_date TEXT PRIMARY KEY,
  is_open    INTEGER NOT NULL,
  source     TEXT NOT NULL
);

CREATE TABLE provider_health (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  provider TEXT NOT NULL, at INTEGER NOT NULL,
  ok INTEGER NOT NULL, latency_ms INTEGER, error TEXT
);
CREATE INDEX idx_health_at ON provider_health(at DESC);

CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);  -- schema_version 等
```

**schema v2（`002_shadow.sql`，M4）追加的影子运行四张表**（全文见迁移脚本，那里逐条写了理由）：

```sql
shadow_order     -- 待成交委托：T 日收盘产生，T+1 开盘成交。一只标的最多一张
shadow_position  -- 模拟持仓：双轨价格 + 峰值 + 最后收盘 + 持有根数
shadow_trade     -- 已平仓的一笔（= 一次卖出；减仓会把一次建仓拆成多行）
shadow_equity    -- 每交易日一行的组合净值。trade_date 作主键 = 天然幂等
```

三组表答三个不同的问题，**合表会让答案再也分不开**：

| 表 | 回答 |
|---|---|
| `signal` | 引擎判了什么 |
| `alert_log` | 有没有真的提醒我，没提醒是被哪道闸门挡的 |
| `shadow_*` | 若按这些信号操作，到今天赚没赚 |

第三个与前两个刻意脱钩：**被提醒层闸门挡掉的信号照样进影子组合** ——
影子量的是**策略**，不是提醒策略。（但**风控硬抑制**的信号不进：那是「无执行意义」，
照它下单等于把不该执行的信号算进绩效。这两句看着像一回事，其实是相反的两个决定。）

### 4.3 数据保留与体积

| 表 | 保留策略 | 估算 |
|---|---|---|
| `kline_daily` | 每只保留 1500 根（≈6 年），超出裁剪 | 100 只 × 1500 × ~120B ≈ **18 MB** |
| `indicator_daily` | 保留 500 根 | ≈ 25 MB（payload 是 JSON，体积主要在这） |
| `signal` | 保留 2 年 | < 5 MB |
| `alert_log` | 保留 1 年 | < 2 MB |
| `provider_health` | 保留 30 天 | < 5 MB |
| `quote_tick` | 保留 7 天 | 12 只 × 240 点/天 × 7 ≈ **< 3 MB** |
| `trade_log` | **不裁剪** | < 1 MB |
| `shadow_*`（M4） | **不裁剪** | < 2 MB |
| `ai_explain`（v8） | **不裁剪，只能用户手删** | 一条几百字，< 1 MB |

总量目标 **< 100 MB**。启动时执行一次异步 vacuum/裁剪（低优先级、非阻塞）。

> **影子账本刻意不进裁剪表**（`shadow_order` / `shadow_position` / `shadow_trade` /
> `shadow_equity`）。它是前向累积的绩效记录，删掉之后**无法重建**——
> 用历史 K 线补出来的那个叫回测，答的不是同一个问题。体积也不构成理由：
> 一年约 243 行净值 + 几百行交易，比 `provider_health` 一个月还小。
>
> 同一个理由让 `shadow_trade` **不加**指向 `signal(id)` 的外键：`signal` 按 2 年裁剪，
> 加了外键就等于把绩效记录挂在日志保留策略上，裁剪那天会连带删掉影子历史。
> `tests/integration/storage/shadow-repo.test.ts` 有一条用例钉着「裁剪不动影子账本」。

> **`quote_tick` 是唯一一张「可以随便丢」的表**，但它**不进「清缓存」**
> （`app:clearCache` 仍然只动指标缓存 + 过期日志 + VACUUM）。理由是时机：
> 盘中点一次清缓存会把当天已经记下的那段分时抹掉，而那段线**补不回来** ——
> 它不是派生物，是一次性的观测记录。7 天滚动裁剪足够控体积了。

#### `quote_tick`：当日分时留痕（v4）

盘中每轮 tick（30s）已经在拉快照，这张表只是把**本来就拿到了**的最新价顺手落一行，
**不新增任何网络请求**、不碰限流器、不影响 provider 健康度。

> **⚠ 2026-08-14 起它是分时图的兜底，不再是主数据源。**
> 那张图默认画数据源的逐分钟分时（§2.5），这张表只在那一趟拉不到时顶上。
> 它**不要删**：数据源全挂时它是唯一还画得出东西的东西，而它的写入照旧不花请求。
>
> 原先这里写的是「为了画一张图去多发一轮请求会违反 §2.4 的请求礼节」——
> 那句话现在只对**轮询**成立。§2.5 说明了用户触发的那一次为什么是另一回事。

它只服务抽屉「行情」页那张走势图。**引擎、回测、指标一个字都不读它**
（那些一律走 `kline_daily`）。两条写入纪律：

- **`stale` 快照不写。** 取数失败时上层重放的是上一轮缓存，写进去会在图上画出
  一条「其实没有成交」的平线 —— 正是 §2.2 「绝不假装实时」要防的。
- **`ts` 取交易所给的行情时刻**（`Snapshot.at`，三家 provider 都在解析它），
  不用本机时钟。主键 `(code, ts)` 因此成为幂等闸门：盘后还会跑好几轮 tick，
  用本机时钟当键的话每轮都会多攒一个点，而折线图上「点多了」完全看不出来。

由此它**不是完整的分时**：覆盖范围 = 应用开着且取数成功的时段。
渲染层必须把洞画成断线（相邻点超过 5 分钟即断开）并标注覆盖起点，
**不许用直线连过去** —— 那条斜线看着像分时线，但那段时间里什么都没被观测到。
`IntradaySeries.source` 为 `LOCAL` 时走的就是这条路径，那几句文案一个字都不能省：
有坐标轴的图看起来很「正式」，一条半截曲线被当成全天的概率比想象中高。

#### `position` 上的三列止损确认（v9）

`stop_floor` / `stop_ack_at` / `stop_ack_loss` —— 用户确认「接受这一段亏损」后重画的
固定止损线、确认时刻、以及**当时的浮亏百分比**。规则与边界在 docs/05 §2.3，
这里只记三条存储口径：

- `stop_floor` 是**不复权绝对价**，与 `cost` 同一口径（§2.3）。用前复权价会让除权那天
  凭空触发或凭空不触发，而症状是「明明没跌到就提醒我了」。
- `stop_ack_loss` 不是冗余：只存那条线的话，日后反推不出「他当时是在 −8% 确认的
  还是 −25% 确认的」—— 一个是正常止损让路，一个是深套了还在扛，完全是两件事。
- **加仓（`PositionRepo.set`）与清仓必须把三列清空。** 成本变了旧线就不再是同一个判断；
  清仓后留着，下次建仓会莫名其妙地不提醒 —— 而少发的错误用户发现不了。

#### `ai_explain`：AI 解读历史（v8）

一条已完成的 AI 解读。抽屉里那份「这只票的全部解读」读它，而它同时干着第二件事：
**挡重复计费**。

原先这块只有内存 LRU，理由写的是「AI 解读花钱但**可重来**」—— 那句话的后半截是错的：
重来要**再花一次钱**，而重启一次内存就空了。于是同一条信号会被反复计费，
且「上次 AI 怎么说这只票的」永远答不上来。现在 `AiService.explain()` 按
**内存 → 这张表 → 真发请求** 的顺序找。

四条：

- **不加任何外键。** 不指向 `signal(id)`：`signal` 按 2 年裁剪而这张表不裁剪，
  加了就等于把花过钱的记录挂在日志保留策略上（与 `shadow_trade` 同一条）。
  不指向 `watchlist(code)`：把票移出自选不该让历史解读跟着消失（与 `trade_log` 同一条）。
- **信号字段（方向 / 阶段 / 置信 / 当时价 / 信号时刻）冗余存一份**，正因为没有外键。
  两年后原信号被裁掉，历史列表若还去 join，剩下的会是一串没有上下文的正文。
  `model` / `protocol` 同理 —— 换个模型再解读一次，结论不同是正常的，
  不标出来的话两条打架的解读会让人以为软件出了错。
- **只有 `done` 才落库。** 用户点了停止的那半截不存：一段截断的解读放进历史里，
  日后翻到时既不知道它为什么短，也不知道结论完不完整。
- **不进 `pruneAll`，也不进「清缓存」，删除只有 `ai:remove` 一条路**（主进程先弹系统确认框）。
  自动删掉一条花过钱、且重新生成还要再花一次钱的东西，而用户完全不知道发生过 ——
  那是最坏的一类。

落库**不改变 AI 的定位**：存的是解释文本，它照旧不回流到信号、闸门、状态点或影子运行。

#### `trade_log`：成交流水（v7）

`position` 答的是「我现在持有什么」（当前股数 + 摊薄成本），**卖出之后那笔赚亏就消失了**，
清仓后连持仓行一起没。这张表答「这只票我总共赚了多少」。

记账口径的唯一实现是 `src/main/trades/ledger.ts`（纯函数，UI 试算与落库共用它）：
买入按加权平均摊薄且**含手续费**；卖出只减股数、**成本价不动**，差额结转成 `realized`。
费率复用 `src/backtest/costs.ts`（与影子运行、回测同一口径，三边数字才能横向比），
但**不套 `buyFill` / `sellFill` 的滑点** —— 用户填的就是真实成交价，再偏一次等于把它改坏。

三条：

- **不加外键，也不进裁剪。** 账本是用户自己的东西，不该挂在自选列表的生命周期上：
  卖光之后把票移出自选，「总共赚了多少」不该跟着消失。
- **`realized` 为 NULL 与为 0 是两回事**：买入没有已实现盈亏，刚好打平才是 0。
- **删一笔要按剩余流水重放重建持仓**，不做反向增量 —— 卖出不改成本价，没有可逆信息。
  重放的前提是**期初那一笔已经补上了**：v7 迁移把每条既有 `position` 转成一行 `OPENING`，
  配置导入也做同一件事。那笔的 `fee = 0` 是「不知道」，不是「没有」。

### 4.4 迁移

`meta.schema_version` 驱动的顺序迁移脚本（`001_init.sql`、`002_xxx.sql`…），只前进不回退。迁移前自动备份 `market.db` 为 `market.db.bak-<version>`，保留最近 1 份。

**当前最新版本是 v7**（`007_trade_log.sql`，见 §4.3）。v5（`005_watch_verdict.sql`）给 `watch_point` 加了
`verdict` / `verdict_text` 两列 —— 记住「建这个观察点时那条解读判的是什么方向」。
两列而非一列：枚举用来上色与归类，原文用来回答「当时到底是怎么说的」，
合成一列必然牺牲其中一个；**`verdict` 允许为 NULL 且那不是错误**
（归一化白名单认不出就留空，绝不猜）。
v6（`006_alert_repeat.sql`）给 `alert_log` 加了 `repeat_count` / `last_at`，
把重复裁决合并到同一行（见 docs/05 §4 的口径修正）。

v4（`004_quote_tick.sql`）：加了 `quote_tick` 一张表（见 §4.3），
不改动前三版的任何表，也**不加任何外键** —— 它按 7 天滚动裁剪，而 `signal` 留 2 年、
`watchlist` 是用户数据，挂上去只会多一处要小心的删除顺序，换不来任何完整性保证。
v3（`003_watch.sql`，P2 续）加的是 `watch_point`；v2（`002_shadow.sql`，M4）是影子运行的四张表。

> `watch_point` 的两个外键（→ `watchlist`、→ `signal`）带来两处**删除顺序**约束，
> 顺序错了的症状是运行时 `FOREIGN KEY constraint failed`：
> ① `WatchlistRepo.remove()` 要先清观察点再删自选（与持仓同一处）；
> ② `pruneAll()` 要先清**已结束**的观察点，再删信号；而**还被观察点引着的信号不能删**
> —— ACTIVE 的观察点刻意不被裁剪（那是用户明确要跟踪的东西），
> 于是它的来源信号也要跟着留。`tests/unit/main/watch-repo.test.ts` 三条用例钉着这些。

`engine_version` 与 schema 分离：策略参数或指标算法变更时递增 `engine_version`，使 `indicator_daily` 与历史 `signal` 的比较有据可依，并触发指标缓存重算（K 线不重拉）。

**用户在设置里换灵敏度档位也会改变 `engine_version`**（M4：`withSensitivity` 换掉 `combine`
的得分线与票数线 → 参数指纹变），于是指标缓存作废重算、影子运行暂停累积。
那不是副作用而是必须如此：两套参数下的指标值在库里长得一模一样，混用等于伪造历史。

### 4.5 周期备份（M4）

§4.4 那个是**迁移前的一次性保险**，只留 1 份，防的是「迁移脚本写错了」。
这一节是**周期快照**，防的是与迁移无关的事故：库被写坏、误删自选、磁盘坏块。

- 落在 `<数据目录>/backups/market-YYYY-MM-DD-HHmm.db`（本地时间，不是 UTC ——
  用户在文件管理器里按名字找「上周三那份」，UTC 会让晚上的备份显示成第二天）
- 保留最近 3 份；**认不出名字的文件一律不删**（与日志清理同一条纪律：
  误删用户自己放进来的文件比多占几十 MB 贵得多）
- 自动备份挂在**休市维护**里（与裁剪同一处、排在它之后），间隔 7 天；设置页有「立即备份」
- **走 `VACUUM INTO` 而不是拷文件。** WAL 下 `market.db` 不是自足的，最近的写还在 `-wal` 里 ——
  拷主文件会得到一个少了最后几分钟数据、**却照样能打开**的库，那种备份最坏，
  因为它看起来成功了。`VACUUM INTO` 由 SQLite 保证一致性快照，且可以在运行中做
  （不必像迁移备份那样先关连接），顺带压掉裁剪留下的空洞。
- 自动备份失败只 warn 并**记下时刻**：不记的话每一轮 tick 都会重试一次同样会失败的备份，
  把日志刷满。手动备份则把失败原因显示给用户（同一分钟内点两次会撞「文件已存在」，
  那是用户自己能理解并绕开的）。

## 5. 代码规范化

用户输入的代码形态五花八门（`600000`、`sh600000`、`600000.SH`、`SH600000`）。统一在入口规范化为内部形式 `SH600000` / `SZ000001` / `BJ430047`，各 provider 在自己的适配层转换成外部形态。规则：

| 前缀 | 市场 | 板块 | `Board` |
|---|---|---|---|
| 600/601/603/605 | SH | 主板 | `MAIN` |
| 688 | SH | 科创板 | `STAR` |
| 000/001/002/003 | SZ | 主板（含原中小板） | `MAIN` |
| 300/301 | SZ | 创业板 | `GEM` |
| 430/920/83/87/88 | BJ | 北交所 | `BSE` |
| 51x/56x/58x（SH）、15x/16x（SZ） | SH / SZ | ETF/LOF | `ETF` |
| 000（SH）、399（SZ） | SH / SZ | 指数 | `INDEX` |

无前缀时按上表推断市场；歧义（如 5 位或非法长度）直接拒绝并提示。

两条实现补充（`src/core/code.ts`，M1）：

- **920 段**是北交所自 2023 年起启用的新代码段，初版表里没有，按公开市场规则补上。
- **指数段必须带显式市场**。`SH000300` 与 `SZ000001` 的六位数字在同一段上，裸 `000300` 按表推断只会得到「深市主板个股」。所以推断路径直接排除 `INDEX`：宁可让用户补一个 `SH` 前缀，也不让「沪深300指数」与「平安银行」互相冒充。`INDEX` 无涨跌停，`priceLimits()` 对它返回 `null` 而非 0。
