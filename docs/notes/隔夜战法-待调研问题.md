### A5 · A 股红利税的现行分档

**要查**：这个分档（≤1 个月 20% / 1 个月–1 年 10% / >1 年免税）现在是否仍然有效。

**影响**：决定除权日是「整日剔除」还是「按税后折算」。
预检已经证明**结论对这个选择不敏感**（§1.1 的敏感性表），
所以它不阻塞 F0，只影响报告的严谨度。

### A7 · 腾讯的后复权与不复权两轨，为什么有 2.6% 的日子对不上？

[预检 §1.1](./隔夜战法-可行性预检.md) 实测：39 只 8.5 年里，
`|后复权日收益 − 不复权日收益| > 1%` 的日对有 **1902 个（2.6%）**，
而分红次数期望只有约 330 次（0.45%）。差出来的约 2% 是两条轨之间的不一致。

抽样看过一例：`SH600000` 2019-02-25，不复权 +8.3%（涨停），后复权 +6.7%，
差 1.5% —— 那天不是除权日。

**要查**：拿第三方数据（同花顺/东财 App/交易所）对一下这几天的真实涨跌幅，
判断是**腾讯的后复权轨有问题**还是**不复权轨有问题**。

**影响**：如果坏的是后复权轨，那么**所有**基于 `*Adj` 的回测结论都要重新审视
—— 这不只是隔夜战法的事，而是 M2 那十几轮标定的地基。
**这一条的重要性超出本功能。**

> 预检的结论对剔除阈值不敏感（−0.062% ~ −0.072%），所以它不阻塞隔夜战法；
> 但它可能阻塞别的东西。

### B2 · 若继续：隔夜候选怎么拿到 `signalId`？

**这是核对代码时发现的硬阻塞**，docs/10 原稿没有覆盖：

- `alert_log.signal_id` 是 **NOT NULL 外键**指向 `signal(id)`，且 `foreign_keys = ON`；
- 而 [`signals.ts:251`](../../src/main/engine/signals.ts#L251) 的 `persist()`
  在「方向为 NONE 且没有任何风控裁决」时**不落库**、返回 `id: null`；
- 隔夜候选恰恰经常出现在「主策略什么都没判出来」的日子（一只安静上涨 3.5% 的票）。

→ **没有 signal 行 = 拿不到 signalId = 提醒发不出去**，
而且它是否发得出去取决于「主策略当天恰好有没有落行」，这是最难查的那类耦合。

| 选项 | 做法 | 代价 |
|---|---|---|
| **① 用 `ANNOTATE` 裁决**（推荐） | 隔夜候选往 `verdicts` 里放一条 `OVERNIGHT_CANDIDATE:ANNOTATE`，`persist()` 那道闸门自然放行，落一行 `direction = NONE` 的 signal | signal 表多出 NONE 行 → 面板 `counts` 里 NONE 那一档被抬高。`ANNOTATE` 这个 action 本来就是为「只标注不改方向」设计的（现有用例只有 `LIMITED_DATA`） |
| ② 改表 | 新增 011 迁移：`signal_id` 允许 NULL + 加 `source` 列（SIGNAL / WATCH_HIT / OVERNIGHT） | SQLite 改 NOT NULL 要重建表并迁移历史行；`alert_log` 是审计表，重建有风险 |
| ③ 不发提醒 | 隔夜候选只进面板清单，与 `tTrade` 同待遇（不发提醒、不落库） | 用户必须在 14:20–14:45 主动打开面板 —— 这等于取消了这个功能的全部价值 |

观察点命中走的是**第四条路**：借用它的**来源信号** ID
（[`candidates.ts:153`](../../src/main/alerts/candidates.ts#L153)）。
隔夜候选没有来源信号，所以这条路走不通。

### B3 · 若继续：接受 signal 表被抬高 NONE 计数吗？

B2 选 ① 的直接后果。面板的 `counts` 按 `direction` 分组，
会多出一批 `NONE`。CLAUDE.md 有一条纪律是
「观察点命中不许写进 signal 表，否则『今天引擎给了几条信号』再也答不准」。

隔夜候选与观察点**不同**：它是引擎（风控层）算出来的，不是用户设的条件。
所以把它算作「引擎判了什么」在语义上站得住。但计数确实会变。

**要决定**：接受，还是给 `counts` 加一条「排除纯标注行」的规则
（后者要动 `shared/signal-group.ts`，那是渲染层与主进程共用的纯函数）。
