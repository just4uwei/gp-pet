## 2. 三家数据源的验证状态不同（**最重要的一条**）

| 源 | 角色 | fixture | 状态 |
|---|---|---|---|
| tencent | 备源 | 真实响应录制（2026-08-11） | 已核对 |
| sina | 备源 | 真实响应录制（2026-08-11） | 已核对 |
| **eastmoney** | **主源** | **手写骨架** | **未核对** |

开发机访问 `push2.eastmoney.com` / `push2his.eastmoney.com` 时连接被对端直接断开，
无法录制。手写 fixture 的**价格与成交量取自同日的腾讯真实响应**（数值是真的），
但 **JSON 结构与字段号是推断的**。

> **2026-08-12 更正：上一段的诊断（「出口网络对该 API 的拦截」）是错的。**
> 那个结论建立在 curl 上，而 curl 对这两个域名 100% 失败、node fetch（undici，
> 也就是应用真正用的客户端）**6/6 成功**，延迟 237–405ms。`provider_health` 里
> 今天的记录是 83 成功 / 24 失败（≈78%），失败症状 `other side closed` 随机出现、重试可过。
>
> 即：**eastmoney 是间歇性失败，不是被封锁**；判断它的可用性不能用 curl。
> `pnpm fixtures:record -- --provider eastmoney` 现在能部分成功（4 个请求里通常成 2 个），
> 但该脚本**没有重试**，要录全得先给它加上 —— `scripts/fetch-history.mjs` 里有现成的
> 三次退避重试可以照搬。录完仍需人工比对字段号与单位。

> 后果：eastmoney 的解析器只能证明「对这个形状的输入处理正确」，不能证明真实响应就是这个形状。
> 出厂优先级把 eastmoney 排在首位，若字段号推断错了，首次联网会走降级到 tencent —— 功能不断，
> 但健康度出口条件（>99%）会挂在主源上。

**首台能访问该接口的机器上必须做**：`pnpm fixtures:record -- --provider eastmoney`
→ 人工比对字段号与单位 → 更新 `src/main/providers/eastmoney/NOTES.md` 的「最后核对」。
细节见 [tests/fixtures/providers/eastmoney/README.md](../../tests/fixtures/providers/eastmoney/README.md)。

同理，**`pnpm dev` 未在本机跑通**：better-sqlite3 是原生模块，需要 `electron-rebuild`
（CLAUDE.md）。typecheck + build + 全部测试绿 ≠ 能启动 —— M0 就踩过两次这个坑。
M1 的验收清单第 0 节因此把「真启一次」列为先决条件。

## 4. 结构上的取舍

### 4.1 SQLite 驱动加了一层薄壳（`src/main/storage/driver.ts`）

docs/03 直接写 better-sqlite3。实现时抽出 `SqlDriver` 接口，原因两条：

1. 原生模块在 Electron ABI 下重建失败时，应用应当**降级**而不是启动即崩 —— 有这层壳才有降级的位置。
2. Vitest 跑在 Node 里，Electron ABI 的 `.node` 在那儿加载会段错误。测试注入 `node:sqlite`，
   被测的是我们的 SQL 与迁移逻辑 —— 而那正是要测的东西。

代价：**只能用位置参数（`?`）**，两种驱动对命名参数的处理不同。已写进 driver.ts 的文件头。

### 4.2 `MarketDataService.getContext` 是同步纯读

docs/02 §4 的数据流图把「缺口 → 增量补齐」画在 `getContext` 里。实现改成由 tick 显式
先 `backfill()` 再 `getContext()`。理由：取数藏在读接口里会让每次读的耗时不可预测，
而且一轮里多处读同一只就会重复回补。现在 `getContext` 不发请求，M2 的引擎可以放心地随便读。

### 4.3 tick 的判断逻辑独立成 `src/main/engine/tick.ts`

`data-layer.ts` 只剩接线（undici / SQLite / Electron 路径），不做判断，因此排除在覆盖率统计外。
「休市一个请求都不发」「日线补齐了就整轮跳过」「探测轮拿真成交纠正日历」这些必须能用假依赖跑出来，
不能只靠真机启动一次来验证。

## 5. 文档没写、但实现绕不过去的

### 5.1 交易日历的探测轮 + `verifiedYears`

docs/03 §3 只给了「db > 内置表 > 周一至周五」三级判据，没说**内置表本身可能是错的**。
`resources/data/holidays.json` 出厂 `verifiedYears: []` —— 表里的 2024–2026 三年是按公开
安排填的，**没有逐条对过交易所公告**。没进 `verifiedYears` 的年份，日历结论一律带
`uncertain: true`：

- Scheduler 在这些日子里每 30 分钟发一次**探测轮**；
- 探测到真成交（`!suspended && last > 0 && volume > 0`，响应成功不算证据）就
  `calendar.markObserved(date, true)` 纠正日历，下一跳回到正常轮询；
- 面板提示「交易日历尚未核对」。

设计原则：**「不知道」绝不当成「休市」**。把交易日误判成休市 = 整天不取数，代价远大于
在真休市日多发几个探测请求。

### 5.2 `attemptDeadlineMs` 与回补的自限并发

registry 对单个 provider 的一次「取数动作」设 20s 上限（一次动作可能含多个请求：日线要拉
原价 + 复权两趟、快照要分片）。

**踩过的坑**：这个计时器从**派发**时起算，而请求会在 HttpClient 的并发闸门（全局 ≤4 / 单源 ≤2）
里排队。若把全部自选股的回补一次性发出去，排在队尾的会在还没发出时就超时，**把健康的源误判成故障**
并触发熔断。所以 `MarketDataService.backfill` 自己限并发（默认同时 2 只 = 4 个在途请求），
与全局闸门对齐。有测试断言峰值并发。

### 5.3 `ProviderRegistry.setPriority()` 原地改而不是重建

用户改数据源优先级时若重建 registry，会**丢掉熔断状态** —— 刚熔断的源立刻又被当成健康的试一遍。
另外：设置里少写一个源不等于「永久禁用」它，`setPriority` 会把没列出的源补在末尾。

### 5.4 快照失败不抛给调度器

docs/03 §2.2 要求「全部源不可用 → 返回上一轮缓存 + `stale: true`」。实现照做：`refreshSnapshots`
不抛异常，而是返回缓存 + `stale`，面板显示「行情离线」并把价格灰显。抛给调度器会让这一轮的
日线回补成果也一起白费。

### 5.5 腾讯的前复权是「减价差」，不是「乘比例」

实测：腾讯 `qfq` 是加性的。而盘中临时 K 线的复权系数是从上一根**乘法外推**的
（`src/core/candle.ts`），两者口径不同。

后果：`adj_factor` **只能**用于「同一根 K 线的复权口径是否变了」这类漂移检测
（`detectAdjustmentDrift`），**不能**当复权系数去反推原价。盘中那一根的复权价因此会有微小偏差
—— 接受它，因为与已存序列的连续性更重要（一根不连续的临时线会直接伪造出金叉死叉）。

## 7. 真机运行观察（2026-08-15）

前两个交易日（08-13 周四、08-14 周五）跑完之后，`pnpm iterate` 把两件事报进了
「**现在就能做**」桶。**逐条查下来，两条都不是工程缺口** —— 记在这里，
免得下一轮会话再查一遍（看板只看得到计数，看不到「迁移什么时候跑的」「代码什么时候落地的」）。

### 7.0 读日志前必须先知道：本机时区是 UTC+7

`git log --date=iso` 记的是 `+0700`；而日志里 `[2026-08-14 14:00:08] [alert] SETTLE：发出 0 条，静默 3 条`
对应 `signal` 表里北京时间 `15:00:07` 那一批 —— 两处独立印证。

**日志时刻要 +1 小时才是北京时间。** 按字面读会得出「SETTLE 窗口跑在 14:00」这种错误结论，
而真实情况是它精确地跑在北京时间 15:00。

> 这正是 CLAUDE.md 里 `shanghaiDayStartMs` 那条纪律设想的 UTC+7 场景 —— 开发机真的在那一档，
> 不是假想。凡是用 `date(created_at/1000,'unixepoch','+8 hours')` 查库的读数是对的，
> 凡是直接读日志时间戳的读数要自己 +1。

### 7.1 `CONFIRMED = 0`：补跑代码至今一次机会都没有过

`signal` 表 769 行**全部**是 `PROVISIONAL`，`indicator_daily` / `shadow_equity` /
`shadow_trade` / `shadow_position` 四张表全空。这几件是同一个因的果
（`reconcile` / `cacheIndicators` / `carryover` 都以 `CONFIRMED` 为前提）。

原因是时序，不是缺陷：

| 事件 | 时刻 |
|---|---|
| 库里仅有的两个交易日 | 08-13 周四、08-14 周五 |
| `engine/settle.ts`（次日盘前补跑）落地 | **08-14 17:18 本地** —— 那个交易日**结束之后** |
| 08-15 | **周六**，没有盘前那一跳 |

⇒ 两个交易日的盘前都没有这段代码，而之后没有再出现过盘前窗口。
**第一次执行机会是 2026-08-17 周一盘前。**

**判据**：周一跑完之后 `CONFIRMED` 仍为 0 才是复发，那时要立刻查 `engine/settle.ts`。
在此之前它不是问题。

### 7.2 `would_block` 全 NULL：迁移比数据晚

- `011_alert_gate` 的迁移**在 2026-08-15（周六）14:56:55 本地才执行**（日志明写 `迁移完成 → v11`）。
- `alert_log` 那 1203 行全部产生于 08-13 / 08-14 —— **那时这两列还不存在**。

所以全 NULL 是必然结果。**并且写入路径是完整的**，已逐处核对：
[`dispatcher.ts`](../../src/main/alerts/dispatcher.ts) 无论前置闸门有没有拦下都算完四道
→ [`service.ts`](../../src/main/alerts/service.ts) 把 `wouldBlock` 带进落库行 → `011` 落列。

⇒ 看板提的两个可能（「迁移没跑」「分发路径没写」）**都可以排除**。同样等周一。

### 7.3 顺带记一个与启动方式有关的资源缺失

08-15 16:22 那次启动报了两条 warn：`resources/data/holidays.json` 与托盘图标读不到，
路径都是 `out/main/resources/...`。

成因是 `app.getAppPath()`：`pnpm dev` 下它指向仓库根（`resources/` 在那儿，正常），
而直接跑 `out/` 时它指向 `out/main`，那底下**没有** `resources/`（构建配置里没有拷贝步骤）。
打包产物不受影响 —— `electron-builder.yml` 的 `extraResources` 配了 `from: resources`。

后果限于「直接跑 `out/`」这一种启动方式：日历退到 `weekday` 兜底（§5.1 的三级判据只剩两级，
结论恒带 `uncertain`），托盘退到 `fallback-icon.ts` 的内置位图。
**两者都是既有的容错路径，不会让功能断**，因此不急着改；但真机验收若用这种方式启动，
`calendarUncertain` 会恒真，读数时要知道原因。
