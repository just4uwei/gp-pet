## 1. 为什么不用 curl 测（这条决定了整份实测的可信度）

CLAUDE.md 记着一条教训：同一个 eastmoney 接口，**curl 100% 失败而 undici 约 78% 成功**。
用 curl 判断可用性会得到相反的结论。

所以探针走 `node:fetch`（undici），与 `src/main/net/http.ts` 的传输层同一族。
**下一轮补样本时也必须用它，不许图省事换 curl。**

## 2. N0-c · 接口形状（已定）

`stock_list` 上限探测借用 `params/universe-broad.json` 的 264 只（只借真代码，与标定无关）：

| 请求只数 | 延迟 | 返回条数 | 覆盖只数 | 混入未点名 |
|---|---|---|---|---|
| 1 | 246 ms | 100 | 1 | 无 |
| 4 | 489 ms | 100 | 4 | 无 |
| 10 | 148 ms | 100 | 10 | 无 |
| 20 | 319 ms | 100 | 17 | 无 |
| 40 | 223 ms | 100 | 32 | 无 |
| 60 | 144 ms | 100 | 36 | 无 |
| 100 | 236 ms | 100 | 28 | 无 |
| **200** | 250 ms | 100 | 24 | **无** |

**四条读数：**

1. **`stock_list` 至少到 200 只不混入** ⇒ 100 只自选 = **一次请求**，不必分批。
2. **单页上限就是 100**（要 200 也只给 100）。分页 `page_index=1/2` **无重叠**。
3. **返回是跨标的、按发布时刻倒序的扁平流** —— 所以「覆盖只数」随请求只数增加反而下降
   （少数活跃公司占满整页）。⇒ **只取第一页会漏票，必须翻页到 `sinceMs` 为止。**
   这条直接决定了 `fetchAnnouncements` 的写法。
4. **`total_hits` 在 40 只以上被截断成 50000**，是个上限不是真值，**不要拿它当计数**。

### 2.1 两个时刻的语义（这条最容易写错）

```
display_time 2026-08-14 17:30:24:703  →  notice_date 2026-08-15 00:00:00
display_time 2026-08-14 16:51:06:319  →  notice_date 2026-08-15 00:00:00
```

- `display_time` = **真实发布时刻**（毫秒用**冒号**分隔，不是小数点）。
- `notice_date` = **归属的公告日**，是发布日的次日。

⇒ 切「昨收盘之后到现在」这个窗口**必须用 `display_time`**；`notice_date` 只用于展示。
按 `notice_date` 切会把昨晚 17:30 发的那批算成今天发的，
症状是盘前简报漏掉一整晚的公告，而**界面上不报错，只是少了东西**。

## 4. 实测顺带查出的一个真 bug（已修）

用**真实响应**跑一遍端到端时（fixture 是手写的，不算数），编排层丢了 **8 条**。查下来是我自己的解析器：

原写法 `splitCode('SH'+digits) ?? splitCode('SZ'+digits) ?? splitCode('BJ'+digits)`，
而 SH 的代码段表里有 `['000', 'INDEX']` ⇒ **`000157`（中联重科，深市主板）
被判成 `SH000157`（上证指数段）**。

后果是**整个深市 000 段**（000001 平安银行、000002 万科…）的公告都带着错代码出来，
被编排层的「未点名的票」防线丢掉 —— **用户永远看不到这些票的公告，而界面上完全看不出来。**

**修法**：`ann_type` 优先（实测可靠：`A,SHA` / `A,SZA` / `A,CYB`），
退化时走 `parseCode` —— 它本来就做对了这件事（`src/core/code.ts`：「指数段排除在推断之外」）。
修后同一请求：100 条全部在点名范围内、丢弃 0，`SZ000157` 的 8 条回来了。
`resolveAnnounceCode` 有三条用例钉着。

> **两条可复用的教训**：
> ① 早先注释里「`ann_type` 只是分类标签，不是可靠的市场位」是**我猜的**，
>    而这个猜测直接把我引向了错路 —— 猜出来的判断不该写成注释里的断言；
> ② **fixture 全绿不等于对**。这个 bug 在手写 fixture 上永远暴露不出来，
>    是拿真实响应跑一遍才掉出来的。与 M1 §2「eastmoney 的 fixture 是手写的」同一条。

## 5. N0-a/b · 成功率与延迟（**只有休市日一档**）

| 时段 | 日期 | eastmoney | cninfo | P50 / P95 |
|---|---|---|---|---|
| `CLOSED_DAY` | 2026-08-15（周六） | 8/8 | 8/8 | 137 / 170 ms · 119 / 203 ms |

**这一档不足以下结论。** 公告接口的负载高峰恰恰在盘后（15:00–18:00，实测那批公告
的 `display_time` 集中在 16:15–18:54），而那正是还没测的时段。

**补样本的做法**（每个时段各跑一次，脚本会自己累加并提示还缺哪个时段）：

```bash
node scripts/probe-announcements.mjs            # 跑一轮
node scripts/probe-announcements.mjs --report   # 只看累计，不发请求
```

**达成条件**：四个时段都覆盖到、连续 ≥ 3 个交易日。到那时回来改本节，并在 §0 去掉「有条件」。
