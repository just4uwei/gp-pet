## 0. 结论先说

**可以做，而且这是消息面在本项目里唯一安全的落点。但它的成败 100% 在取数那一段，不在 AI。**

| # | 判断 | 依据 |
|---|---|---|
| 1 | **「盘前/盘后单独一屏、只提醒关注、不进信号」这个约束把整件事从「新增一层引擎」降级成「新增一屏内容」** | 不进 `signal` 表、不进闸门、不进影子运行、不进回测 ⇒ 不新增任何需要标定的参数 ⇒ 不欠回测债。这正是 `src/main/ai/` 的既有定位 |
| 2 | **机器是现成的** | [010_report_note.sql](../src/main/storage/migrations/010_report_note.sql) 已跑通「一天一条 + `trade_date` 主键做幂等闸门 + 只有 done 落库 + 不进裁剪 + 事实指纹标过期」；[ai-target.ts](../src/shared/ai-target.ts) 已跑通「同一条 IPC 通道分发两种任务」 |
| 3 | **数据层完全没有这个能力** | `QuoteProvider` 只有五个方法（`fetchDaily` / `fetchSnapshots` / `fetchProfile` / `fetchMinutes` / `fetchCalendar`）。整个 [src/main/providers/](../src/main/providers/) 里 `news\|announce\|公告\|资讯` **一个文件都没命中** |
| 4 | **AI 客户端不能自己去找** | [client.ts](../src/main/ai/client.ts) 是纯 POST + SSE，没有工具调用、没有联网检索。`tool_use` 在 [protocols.ts:191](../src/main/ai/protocols.ts#L191) 只出现一次，而且是「**跳过**它，只拼 text」 |
| 5 | **所以「没有输入的 AI 消息面报告」不是弱功能，是会骗人的功能** | 现有两份提示词都明写「不要凭记忆补充这只股票的基本面、消息面」（[prompt.ts:28](../src/main/ai/prompt.ts#L28)、[prompt.ts:129](../src/main/ai/prompt.ts#L129)）。用户会把一条编出来的「监管处罚」当真去卖股票，而界面上完全看不出是编的 |
| 6 | **取数这条实测通了，而且比预想的好** | 东财公告接口 200 / 130 ms，**多只票一次查**，且**数据源自己已经把公告分好类**（`column_name` = 业绩快报 / 关联交易 / 分配预案 / 回购进展…）。数字见 §4.2 |
| 7 | **因此原文第二章（NLP 事件识别、情感分析、RexPrompt）在本场景整章用不上** | 它解决的是「给全市场新闻打分」；本功能要答的是「我这几只票昨晚出了什么公告」。公告是事实、有标题和类型就够，不需要把非结构化文本"转化为结构化" |
| 8 | **worldmonitor 不用** | 三条实测：两个域名从本机 20 s 超时；389 个 RSS 允许域名里中国大陆源 **0 个**；AGPL-3.0。见 §1.3 |

**因此本需求的形状是**：先把公告源的稳定性量出来（N0），
同时把**不依赖任何新数据源**的「今日环境陈述」先做掉（N1），
再做「自选股公告清单」（N2/N3/N5）。**N4（AI 点评）后来决定不做**，见该节。
**永远不做**：接进提醒闸门、给买卖方向、下载解析公告正文、做全市场消息扫描。

## 1. 来源与采纳边界

### 1.1 采纳什么

- **一个分类结构**：盘外因素分「全球指数 / 政策法规 / 地缘政治 / 企业消息面」四类。
  这个拆分有用，因为**四类的可得性与可操作性差得很远**（§4.1 的表就是按它排的）。
- **一条产品判断**：盘外因素应当与技术指标**分开呈现**，而不是揉进同一个得分。
  原文自己在第三章走的是相反的路（「事件因子与技术指标的权重分配」「XGBoost 自动优化权重」），
  本项目不采纳那条 —— 理由见 §2.2 与 §2.3。
- **一条风险提醒**：原文第六章第 4 条「黑箱依赖与过度信任」，与本项目「AI 只读、不回流」是同一条立场。

### 1.2 不采纳什么（逐条点名）

| 原文内容 | 为什么不用 |
|---|---|
| 「传统策略回撤 12% / 政策驱动 5% / 复合策略 3%」 | 无标的、无区间、无样本量、无成本口径。ADR-0003 要防的正是这个形状 |
| 「传统财报策略亏 25% / 消息驱动赚 15% / 复合赚 10%」 | 同上，且是单点案例、事后挑出来的 |
| 「投入 2 万–5 万条标注数据，F1 从 85% 提升至 93% 以上」 | 与本功能无关（§0 第 7 条：本场景不需要 NER），且数字无出处 |
| 影响分级「I 级特别重大 / II 级重大 / III 级较大 / IV 级一般」 | 是行政应急预案的分级语言，不是市场影响的可测量定义。落进 UI 会变成一个没有依据的权威标签 |
| 「−1 到 1 的连续影响评分」「30 天公告叠加效应」「Top 20% 公告质量分」 | 全部是转述阈值。**本功能一个评分都不做**（§2.2），所以这几个数连 `GUESS` 都不必落 |
| Kafka / Flink / FPGA / C++ 执行层 / 毫秒级延迟 | 本项目是单机 Electron + SQLite，不接券商、不下单，整章不适用 |
| 「粒子群优化动态调参」「三层四维风险评估框架」 | 与 [09](./09-下一阶段开发计划.md) §5「明确不做贝叶斯优化」同一条理由，且更远 |

> **另有两件转换时查实的事**，记在[归档件](./reference/量化交易盘外因素处理.md)头部：
> 原文四处「技术实现：」小节**全部是空的**（文档里没有任何图片或文本框，`w:drawing` / `w:pict` 计数均为 0），
> 而 105 条参考来源里混着电化学废水处理、生物学 Glauber 动力学、临床 NLP 等无关文献。
> 这不改变 §1.1 那三条采纳项的价值，但它决定了**这份文档只能当问题清单，不能当方案依据**。

### 1.3 worldmonitor 为什么不用（三条实测，2026-08-15）

| 事实 | 实测 |
|---|---|
| **托管端点不可达** | `worldmonitor.app` 与 `api.worldmonitor.app` 各试 20 s 全部超时（`http=000`）。同一时刻 `api.github.com` / `raw.githubusercontent.com` 均通 ⇒ 不是本机断网 |
| **覆盖不对口** | `shared/rss-allowed-domains.json` **389 个允许域名，中国大陆源 0 个**（关键词命中的 4 个是 `rss.cnn.com` / `www.cnbc.com` / `www.techinasia.com` / `www.cnas.org`，`.cn` 子串误报）。`src/config/feeds.ts` 659 条 feed 里涉华的全部是 Google News RSS 代理的英文报道 + 两条 `site:*.gov.cn` 的 Google News 搜索。**没有巨潮、没有证监会、没有交易所公告、没有财联社/东财** |
| **许可证** | AGPL-3.0。整块 vendor 进本仓库会把蹲点拉进传染范围；只调公开 API 不构成衍生作品，但那条路被第一行堵着 |

它最强的一档（地缘政治、基础设施、冲突事件）恰好是本项目形态最用不上的一档。
**这不是它不好，是形态不匹配。** 本文档不再提它。

## 2. 这个功能在答什么

### 2.1 它答的是引擎答不了的那个问题

引擎回答「按这套规则，这只票现在该不该买卖」。它**看不见**公告。
于是有一类真实体验无法解释：**「这只票今天为什么跌破止损线」** ——
可能是趋势走坏（引擎能说），也可能是昨晚出了减持公告（引擎完全不知道）。

本功能只做一件事：**把「引擎看不见的那部分」摆出来，让用户自己判断**。
它不改变引擎的任何结论，也不试图解释引擎的结论。

### 2.2 它为什么必须「只列不判」

事实层只列五样：**哪只票 · 什么时候 · 什么类型 · 什么标题 · 原文链接**。
不打分、不判利好利空、不给买卖方向。三条理由，一条比一条硬：

1. **只有标题，没有正文。** 本功能不下载解析 PDF（§9），模型看到的就是一行标题。
   拿标题判利好利空是在没有依据的情况下下结论，而它读起来会非常像有依据。
2. **两个来源、可能相反的结论，用户没有办法判断该信哪个。**
   这与 [report/build.ts](../src/main/report/build.ts) 的「只复述不推导」、
   [watch-mark.ts](../src/shared/watch-mark.ts) 的「不许读 `watch_point.verdict` 去改方向」
   是同一条纪律，在本项目里已经立过两次。
3. **一旦打分，那个分就是一个参数**，而它无法回测（§7）⇒ 立刻变成一个永久 `UNTESTABLE`
   的、影响用户决策的数。这是 ADR-0003 最不想要的东西。

AI 那一段（N4）**允许**做的是排序与提示：「这几条里，停复牌与减持这两条建议你开盘前先看」。
**不允许**做的是：「这条公告利好，可以关注」。

### 2.3 它为什么不能进提醒闸门

- **配额是全局的**：每小时 ≤ 6 条、每日 L2+L3 ≤ 4 条（docs/05）。
  公告是高频的 —— 实测四只票一次查就返回 20 条。接进闸门会把止损提醒挤掉，
  **而被挤掉的那条止损用户发现不了**。这与[内置行业 ETF 不进闸门](./05-风控与提醒规则.md)是同一形状，且更严重。
- **`alert_log.signal_id` 是 NOT NULL 外键**，而公告不对应任何一行 `signal`。
  硬要发就得凭空造一行信号 —— 那会污染「今天引擎给了几条信号」这个问题的答案。
- **它不是「现在要做决定」的东西。** 提醒的定义是打断；而公告清单是「你打开看一眼」。
  两者不是同一种交互。

**结论**：它是一屏内容，不是一个提醒渠道。不进 `alert_log`、不点状态点、不弹气泡、不占配额。

### 2.4 它为什么不需要回测（与 [10](./10-隔夜战法功能需求.md) 最大的差别）

隔夜战法产出交易决策 ⇒ 有绩效 ⇒ 必须先量（那份文档的 F0 因此是硬闸门）。
本功能**不产出任何交易决策** ⇒ 没有绩效可测 ⇒ 不进 `src/backtest`、不进 `main/shadow`。

它的判据是「用户觉得有没有用」，与 `alert.bubbleScore` 同一档 —— 靠自用一段时间。
详见 §7，那一节同时说明**什么是可以自动验的**（不是绩效，是「有没有编造」）。

## 3. 与现有架构的五处接口

### 3.1 Provider 层：新增取数能力，带三条边界

`ProviderCapabilities` 增一项、`QuoteProvider` 增一个可选方法 `fetchAnnouncements`。三条边界：

1. **绝不设 `emptyIsFailure`。** 绝大多数票绝大多数天没有公告 —— 返回 0 条是**合法的**。
   记成失败会降级三个数据源、跳熔断，把行情 tick 一起拖下水。
   这与 `fetchMinutes` 那条坑（停牌股与开盘前合法返回 0 个点）**完全同形状**，
   [registry.ts](../src/main/providers/registry.ts) 里已经踩过一次。
2. **走 `net/http.ts`，不另起链路。** 它是普通的行情类 GET，与快照取数共用全局限流器是**对的** ——
   一天只跑几次，不会饿死 tick。这与 AI 客户端**必须**另起一套（一次 40 s 的 LLM 调用挂上去会饿死盘中轮询）是相反的判断，两者的差别在耗时量级。
   > ~~要确认的一件事：`net/http.ts` 带 GBK 解码…~~ **已确认没问题（2026-08-15）**：
   > `encoding` 是按次传的、默认 `'utf-8'`（`opts.encoding ?? 'utf-8'`），
   > 而 eastmoney 的 provider 从来不传它 —— GBK 只有新浪与腾讯那两条路显式指定。
3. **不进 tick。** 触发方式见 §3.4。

### 3.2 AI 层：复用 `ai:explain` 通道，加第三个 target 前缀

[ai-target.ts](../src/shared/ai-target.ts) 现在有 `report:<date>` 一个前缀；本功能加 `brief:<date>`。
**格式仍然只在那一处定义** —— 那个文件的头注释已经写清代价：
渲染层与主进程各拼一份的症状是「点了没反应」，或者更糟，走到解释单条信号那条路上、
拿日期去信号表里查、报一句「该信号已不在库中」。

复用带来的东西（都是踩出来的，不要重造）：两层缓存防重复计费、在途去重、取消、流式接续、
**只有 `done` 才落库**。

新增第三份系统提示词 `AI_BRIEF_PROMPT`（[prompt.ts](../src/main/ai/prompt.ts)），
与既有两份并列。它的禁令见 §8。

### 3.3 存储层：两张新表，两种保留策略（别混）

| 表 | 内容 | 能不能重建 | 保留策略 |
|---|---|---|---|
| `announcement` | 从数据源拉到的公告条目 | **能**（再拉一次就有） | **可以裁剪**，进 `pruneAll` |
| `brief_note` | AI 写的那段简报点评 | **不能**（花过钱、模型可能已换） | **不裁剪**，与 `ai_explain` / `report_note` 同一条纪律 |

这条区分不能凭感觉：`ai_explain` 与 `shadow_*` 不裁剪的理由是「无法重建」，
而公告是可重建的，让它无限增长没有好处。**但两张表要分开**，
否则裁剪那天会连带删掉不该删的（[010 头注释](../src/main/storage/migrations/010_report_note.sql)已经记过这个形状）。

其余照抄 `report_note` 的形状：`trade_date` 主键 = 一天一条 = **幂等闸门**
（少了它，同一天点两次「重新生成」会攒出两行，而「历史里多了一条」在界面上看不出来）；
存 `fact_digest` 以便如实说「这段是基于哪一版事实写的」——
**指纹里不许放生成时刻**，否则每次都变、「已过期」提示恒亮（`report-ai.test.ts` 两条钉着同款）。

`announcement` **不加**指向 `watchlist` 的外键：用户删掉一只自选股不应该连带删掉历史公告记录，
而且删除顺序会立刻变成第三处坑（`watch_point` 已经贡献了两处）。

### 3.4 调度层：不进 tick，由用户打开触发

- **不做定时推送。** 盘前 08:30 用户的机器可能根本没开 —— 一个「必须开机才生效」的定时任务
  会静默地时有时无，而用户无法分辨是「今天没消息」还是「今天没跑」。
- **打开就现拉**：用户进入那一屏时，若当天还没拉过就拉一次（`trade_date` 主键天然去重）。
  这与 `quote:intraday` 是同一类「**量由人决定**」的取数，
  因此同样不受 docs/03 §2.4 那份轮询预算约束 —— 前提恰恰是它由人触发。
- **「今天」一律走 [shared/time.ts](../src/shared/time.ts) 的 `shanghaiDayStartMs`**，
  不要写 `setHours(0,0,0,0)`（UTC−5 的机器上本机 00:00 是北京 13:00）。
- **公告时刻按北京时间读写**，与分时那条纪律相同。

### 3.5 渲染层

- **免责与来源标注是固定 DOM，不靠提示词**（既有纪律，[prompt.ts](../src/main/ai/prompt.ts) 头注释）。
- **渲染层不 import `src/main`**；事实层聚合走 IPC，与 `trade:preview` 同一个理由。
- 流式那段状态机用 [useAiStream.ts](../src/renderer/panel/useAiStream.ts)，**不要抄第四份**。

## 4. 数据可得性盘点

### 4.1 按原文四分法，逐类对照本项目

| 类别 | 本项目能不能拿到 | 对本功能的价值 | 结论 |
|---|---|---|---|
| **全球指数 / 隔夜外盘** | ✅ 现有 provider 就能取（港股、美股指数、期指等） | 高 —— 直接影响开盘 | **N1，零新增依赖，可先做** |
| **企业消息面（公告）** | ✅ 实测两个源都通，见 §4.2 | **最高** —— 能解释「这只票为什么今天跌破止损」 | **N2，本功能主体** |
| 政策法规 | ⚠ 要另接政府站点，技术栈差异大、结构不稳定 | 中 | **不做**（§9） |
| 地缘政治 | ⚠ 只有英文二手源，且多数不可达 | 低（日线 / 数只自选 / 不下单的形态用不上） | **不做**（§9） |

### 4.2 公告源实测（2026-08-15，单点）

| 源 | 结果 | 形态 |
|---|---|---|
| 巨潮 `cninfo.com.cn/new/hisAnnouncement/query` | **通**（POST 表单） | 全市场流水；带 `announcementTitle` / `announcementTime` / `adjunctUrl`（PDF 原文） |
| 东财 `np-anotice-stock.eastmoney.com/api/security/ann` | **通，200 / 130 ms** | **按代码查、多只可一次查**；自带 `columns[].column_name` 分类 |

东财那个更对口。实测 `stock_list=600000,000001,600519,300750` 一次返回 20 条、四只票都有：

```
按代码分布: {600519: 6, 000001: 7, 600000: 3, 300750: 4}
公告类型:  业绩快报 / 关联交易 / 分配预案 / 回购进展情况 /
          半年度报告全文 / 半年度报告摘要 / 半年度财务报告 / 其他
```

两个后果：

1. **请求预算不是问题。** 多只一次查 ⇒ 100 只自选约几次请求/天。
2. **不需要 NLP 分类**（§0 第 7 条）。数据源自己分好了。

### 4.3 三件还没验的事（N0 要回答）

1. **`stock_list` 的单次上限是多少。** 决定 100 只自选要拆几次。
2. **多天、多时段的成功率。** 单次 curl 成功**不能**下结论 ——
   eastmoney 那条教训写在 CLAUDE.md 里：undici 成功率约 78%、curl 100% 失败，
   两个客户端的结论可以完全相反。**必须用应用自己的 HTTP 客户端测。**
3. **分页与时间窗口语义。** `notice_date` 与 `display_time` 差一天（实测 `display_time=2026-08-14 18:54` 对应 `notice_date=2026-08-15`）。
   「昨收盘到今开盘之间发布的公告」到底该按哪个字段切，要先定死 —— 切错的症状是漏掉一整晚的公告，而界面上不报错。

### N4 · AI 横向点评 —— **不做（2026-08-16 决定）**

> 原设计是「让模型指出哪几条建议开盘前先看」。**推翻它的不是「公告没用」，是四条别的理由**，
> 按硬度排序：

**① 模型看到的和用户看到的是同一行字。**

现有 AI 解读之所以值钱，是它拿到**用户拼不出来的东西**：子信号明细、触发时的指标值、
闸门结论、参数标定状态 —— 用户看那一屏是看不出这些的。
而公告这里模型拿到的就是那 20 行标题，**用户自己扫一眼是一样的，而且更快**。
没有信息不对称，就没有解读的立足点。

**② 分诊可以确定性地做好，而且已经做了。**

实测 4500 条全市场公告：数据源给了 **175 个分类**，粒度相当细
（不是一个粗桶，而是「担保年度额度预计 / 追加担保公告 / 提供对外担保公告」这种层次）。
N3 的 `SPOTLIGHT_CATEGORIES` 因此改成**按完整分类名精确匹配**，
一次性解决了原先关键词子串匹配的误报（担保类 2.6%、IPO 问询、回购进展、转股停牌）
与漏报（重组进展、终止上市风险提示、警示函、限售股解禁）。
**确定性、免费、即时、可审计、可写用例** —— 这五样 AI 一样都给不了。

**③ 它会被推向判方向，而方向这个维度在本项目数据上没有信息。**

N4-c 原本写了四条禁令，但提示词是**尽力而为**（`prompt.ts` 头注释）。
而 §8.5 的三轮实测已经证明：公告方向（同日 / 事件+滞后 / 股票频率）测不出任何东西。
让模型说「这条值得看，因为可能利好」，是在生产一个**我们自己的数据说不存在**的东西。

**④ 技术上还有一个死结：`reportFactDigest` 会恒亮。**

喂给 AI 就得把公告算进事实指纹，而公告每次拉取都在变
⇒ 指纹每次都变 ⇒「这段已过期」提示永久亮着，等于没有这个功能
（正是 [digest.ts](../src/main/report/digest.ts) 头注释在防的事）。

#### 什么条件下才该重新考虑

**接了正文解析（PDF）之后。** 那时模型第一次拿到用户没有的信息 ——
一份三十页的减持公告里「减持比例、价格区间、锁定期」这些，用户不会去读，而模型能摘。
在那之前，N4 只是把用户已经看得见的东西换个说法。

而正文解析本身在 §9 是「明确不做」（耗时、体积、失败率都不在这个功能的量级上，
且解析出正文之后「不判利好利空」这条纪律会立刻承受压力）。
**所以这是一条真正的连锁依赖，不是随口的推脱。**

> ⚠ **不要因为「AI 那套机器现成的」就把 N4 加回来。** 复用成本低不是做一件事的理由 ——
> `brief:<date>` 这个 target 前缀、`AI_BRIEF_PROMPT` 这份提示词都不必存在。

## 6. 本功能不新增任何引擎参数

**这是它与 [10](./10-隔夜战法功能需求.md) 最重要的差别，也是它不阻塞 [09](./09-下一阶段开发计划.md) 主线的原因。**

- **不动 `src/core/params.ts`** ⇒ 不递增 `ENGINE_VERSION` ⇒ 指标缓存不作废 ⇒ **影子运行不停止累积**。
- **不进 [params-view.ts](../src/main/settings/params-view.ts) 的 `STATUS` 表。**
  那张表答的是「哪个引擎参数有依据」，往里掺进「公告保留 90 天」这种运行配置，那张表就废了 ——
  与「观察点不是策略参数」是同一条边界。
- 本功能确实有几个可调的数（保留天数、拉取窗口、类型白名单），它们全部是**运行配置**，
  住 `AppSettings` 或代码常量，**不是**引擎参数。

> 判据很简单：一个数如果**能影响买卖判断**，它就是引擎参数、必须走标定；
> 如果只影响「显示多少条、留多久」，它就是配置。
> 本功能的所有数都在后者 —— **前提是 §2.2 的「只列不判」被守住**。
> 一旦有人加了「影响评分」，这一节立刻失效，整个功能就要重走 ADR-0003 那套流程。

## 7. 没有回测，那判据是什么

### 7.1 不可自动验的部分：有没有用

与 `alert.bubbleScore` 同一档，判据只能是**自用**：
连续 10 个交易日记录「今天列出几条 / 我真的点开了几条 / 有没有哪条改变了我当天的操作」。
这一条无法用测试替代，也不该硬凑一个数字（[09](./09-下一阶段开发计划.md) §2.1 的 `UNTESTABLE` 那一档就是这个意思）。

### 7.2 可自动验的部分：有没有编造

这才是本功能真正需要盯住的风险，而它**是可以写成用例的**：

- **结构保证**：`announcement` 表里每一条都有原文链接（N2-d 在入库处就丢掉没有链接的），
  UI 上每一条都可点开。**用户随时能自己核对。**
- **用例 1**：给 AI 一份**空**的公告清单，断言不发请求（N4-d）。
- **用例 2**：给一份含 3 条公告的清单，断言提示词里**只有**这 3 条，
  且系统提示词包含 §8 的全部禁令（对齐 `ai-prompt.test.ts` 的既有写法）。
- **用例 3**：断言上下文里带着参数标定状态那一块（`ai-context.test.ts` 已有同款用例钉着）——
  缺了它模型会默认引擎结论经过验证。
- **用例 4**：断言公告条目**不出现**在 `signal` 表、`alert_log`、影子账本里（§2.3）。

**这四条用例合起来回答的是「它会不会骗人」，而那是本功能唯一可能造成实际损害的方式。**

## 8. 措辞纪律（本功能专属，叠加在既有纪律之上）

既有四条（不得称胜率/概率、不得出现必涨抄底稳赚牛股、不得展示未验证绩效、
固定小字「仅供参考，非投资建议」）全部适用。本功能**额外**五条：

1. **不得对任何一条公告说「利好」「利空」「重大利好」。** 见 §2.2。
2. **不得说「今日无异常」「今日平安」。** 没有公告 ≠ 没有消息 ——
   本功能只覆盖公告这一类，说成"无异常"是替一个没查过的范围担保。
3. **「盘外因素」这个词不进 UI。** 用户不用这个词。界面上叫「消息面」或「今日公告」。
4. **不得把公告与引擎信号并成一句结论。** 「公告 + 信号同向，值得关注」这类话
   在展示层与模型输出里都不许出现。
5. **必须显式说明覆盖范围与口径**：「来自 <源名>，只有标题与类型，未解析正文。」
   与「置信度不是胜率」同一条理由 —— 用户需要知道这份东西的边界在哪。

## 8.5 一次已经做完的验证：公告不能用来选股（2026-08-16）

> 起因是「能不能用消息面把全市场缩小到部分个股，再让引擎盘中观测，实现荐股」。
> 全部数字与判据边界见 [M2 §5.25](./notes/M2-偏差报告.md)。

**结论：在现有引擎上不成立。** 判据是打散跨度下的配对胜率（50% = 与随机无异）：

| 分层 | 建仓 | 配对胜率 |
|---|---|---|
| ALL | 1675 | 46.50% |
| **公告 有** | **226** | **51.50%** |
| 公告 无 | 1449 | 48.50% |

比配对胜率更硬的一条：**公告日占全部股票日 14.4%，而建仓落在公告日的比例是 13.5%**
—— 两个数几乎相同，说明引擎的选点与「有没有公告」**正交**。
「用公告缩小范围」因此不改变入场质量分布，只是把样本量砍到 13.5%。

**按方向拆开之后（补测）**：分类器事前定死、只跑一次。

| 分层 | 建仓 | 配对胜率 |
|---|---|---|
| 公告 中性 | 166 | **39.50%** ← 唯一样本量像样的桶，低于随机 |
| 公告 利空 | 35 | 49.50% |
| 公告 利好 | 25 | **78.50%** ← n=25，**不构成证据** |

「利好 78.5%」不能当发现：n=25、88 个分层无多重比较校正、且表内自相矛盾
（`RANGE · 公告 利空` 是 85.5%，比利好还高）。要把它变成证据得把样本量上一个数量级，
且必须先注册判据再跑 —— **本次刻意不追加**，在同一份数据上调关键词表或窗口直到显著，
正是这条纪律要防的事。

**再补：事件 + 滞后确认（10 日窗口，预注册后只跑一次）**——
即「利好公告 → 追踪一段时间 → 引擎出信号才建仓」，比同日巧合更像事件驱动的正常形状：

| 分层 | 建仓 | 配对胜率 |
|---|---|---|
| **公告 利好** | **167** | **32.00%** |
| 公告 中性 | 648 | 32.50% |
| 公告 利空 | 228 | 63.00% |
| **公告 无** | **632** | **65.00%** |

**方向与假设相反**：利好比「无公告」低 33pp。**这同时杀掉了上一格那个 78.5%** ——
同一概念、n 从 25 涨到 167，读数从 78.5% 掉到 32.0%，正是噪音的预期表现。**别再引用 78.5%。**

顺带一个观察（不是结论）：利好 32.0% 与中性 32.5% 几乎相同，而无公告 65.0%
⇒ **方向标签没有区分度，起作用的是「最近有没有公告」本身，且是负向**。
可能是公告密度在代理公司活跃度/波动率，本次测量分不开。

**⇒ 此方向封盘**：两种形状都测过，判据事前定、只跑一次、结果照报。
再动必须换数据，不是换参数。

**这不影响本文档的其余部分。** N1–N5 从来不产出交易决策（§2.2「只列不判」、§2.4「不需要回测」），
这次验证否掉的是**另一个**设想 —— 把消息面接进选股/荐股。
两者的区别正是 §2.2 那三条理由在说的事，现在它多了一条实测支撑。

**⇒ §9「明确不做」因此新增一条：不做「公告选股」。**

## 9. 明确不做

- **不接进提醒闸门**（不进 `alert_log`、不点状态点、不弹气泡、不占配额）。见 §2.3。
- **不打分、不判利好利空、不给买卖方向。** 见 §2.2。
- **不下载解析公告 PDF 正文。** 一次简报会有几十条，解析 PDF 的耗时、体积与失败率都不在这个功能的量级上；
  且解析出正文之后，"不判利好利空"这条纪律会立刻承受压力。要做是另一次独立设计。
- **不做定时推送。** 见 §3.4。
- **不做政策法规与地缘政治的抓取。** 见 §4.1。
- **不做全市场消息扫描。** docs/01 §3 + [P2 评估](./notes/P2-全市场扫描评估.md)。
- **不做公告的 AI 点评**（2026-08-16，见 N4）：模型看到的和用户看到的是同一行标题，
  没有信息不对称；分诊已由确定性的分类白名单做掉。
- **不做「公告选股」**（2026-08-16 实测否掉，见 §8.5 与 [M2 §5.25](./notes/M2-偏差报告.md)）：
  公告日上引擎的配对胜率 51.5%（= 随机），且建仓在公告日上零富集（13.5% vs 基准 14.4%）。
- **不集成 worldmonitor**（vendor 与 API 两条路都不）。见 §1.3。
- **不新增引擎参数、不进 `params-view.ts` 的 `STATUS` 表。** 见 §6。
- **不进回测与影子运行。** 见 §2.4。
- **不做「昨天的简报」翻页。** 与日报同一条理由：`position` 表是**当前**状态，
  拿它配三天前的公告会得到一个错的数，而错的方式用户看不出来。
